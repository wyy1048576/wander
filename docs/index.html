How it works

Four steps from "where should we go" to "book it". Everything after the swipes is the agent's job.

1
Pick a destination, share a code

Tokyo, Kyoto & Osaka, Nara, Kyushu or the whole grand tour. One person starts a room, friends join from their phones with a four-letter code. No accounts.

2
Everyone swipes the same pairs

Twelve pairs of place cards, pick one from each. Pairwise choices give a far stronger signal than like / dislike.

3
See where you clash

Before planning, each person's lean is spelled out, and so are the clashes. Nobody is surprised by the plan.

4
The agent reconciles, connects, books

Muse Spark runs a tool loop over live data and returns one itinerary: every item says whose pick it was and why, trains have times, and a task list covers the chores.

Agent log · muse-spark-1.3

    Every tool call is persisted and streamed to both phones while the plan builds. Plans take about two minutes and 15 to 20 tool calls.

    Not a list of places. A plan you can execute.

    Most AI trip planners stop at "visit Kinkaku-ji". Wander connects the places: which train, from which station, at what time, what to order when you get there, and the chores that have to happen first. Three real items from the plan above.

    Built with

    Two Meta models, three live data sources, one SQLite file. No hosting, it runs on a laptop.

    Meta modelRole
    Muse Spark 1.3The planning agent. Chat completions with function calling: reads both swipe histories, decides the city split, calls the tools below, then finalize_plan with a structured itinerary validated by zod.
    Muse Image 1.0All 40 swipe cards across the five destination decks (Tokyo, Kyoto & Osaka, Nara, Kyushu, grand tour). Generated from prompts in cards.json, so the app carries no third-party photo rights.
    ToolSource
    search_hotelsliteAPI sandbox. Real hotels, live rates, prebook → book with simulated payment.
    search_restaurantsGoogle Places API (New). Rating, reviews, price level, Maps link.
    get_transit_routeGoogle Routes API, transit mode. Live legs where Google has data.
    flight_linkGoogle Flights search link. No live fares.
    Honesty notes
    • Five Japan destinations today, each its own deck and agent brief; more destinations are listed as coming. On the grand tour the agent decides whether the trip is long enough to reach Kyushu, and says so in the tradeoffs when it isn't.
    • Hotel bookings run in liteAPI's sandbox: real hotels and prices, simulated payment, no room is held. The booking screen says so.
    • Flight links are search links, not fares.
    • Google has no transit schedules for Japan through its API, so train legs are marked times estimated and link to the operator (SmartEX for Shinkansen) or Google Maps.
    • Every external call runs through a per-API daily budget and a response cache, so a runaway loop stops itself.
    • Everything in the repository was written during the hackathon window, Oct 26 to Nov 4, 2026.

    Run it locally

    Needs Node 22.13 or newer and three free API keys. The agent runs on your machine, so your keys never leave it.

    # clone and install
git clone https://github.com/wyy1048576/wander
cd wander
npm install

# keys: META_API_KEY (dev.meta.ai), GOOGLE_MAPS_API_KEY (Places API New + Routes), LITEAPI_KEY (sandbox)
cp .env.example .env.local

npm run dev            # http://localhost:3000, open two windows to play both travellers
npx tsx scripts/golden-room.ts import   # or load this exact demo room
